# CTP 行情接入（境内期货公司的程序化接入）

竞赛默认用新浪的 HTTP 行情，够用但有三个硬伤：延迟到分钟级、会被限流、品种一多请求量就线性放大。
接上期货公司的 **CTP 行情**之后这三条一起消失——CTP 是**订阅推送**，登录时一次性订阅全部合约，
之后由行情前置把 tick 推过来，品种再多也不会多发一个请求。

## 一、先拿到凭证

期货公司给的手机/电脑**交易终端**和程序化是**两套接入**，程序化要单独申请：

1. 联系开户的客户经理，说明要开通**程序化交易（CTP 接入）**，通常需要签一份程序化交易承诺书，
   有的公司还要求说明策略类型与报撤单频率。本项目只用**行情**、不下单，可以直接说明是行情订阅用途。
2. 开通后会拿到四样东西，缺一不可：
   - **经纪商代码** BrokerID（例如 `8888`）
   - **行情前置地址** MdFront（形如 `tcp://<前置IP>:<端口>`；生产与仿真是两套地址）
   - **投资者编码** InvestorID（就是你的资金账号）
   - **密码**（程序化接入的密码，可能与终端登录密码不同）
3. 有的公司还会给 AppID / AuthCode（终端认证）。**行情前置不需要这两个**，只有交易前置才要。

> 先用公司给的**仿真/测试前置**跑通，再换生产地址。仿真环境行情延迟大、夜盘可能不开，
> 但足够验证凭证和连通性。

## 二、安装 SDK

```bash
pip install openctp-ctp
```

Windows 有现成 wheel，装完即可用。本项目只依赖它的行情部分（`openctp_ctp.mdapi`）。

## 三、配置

`config/config.yaml`（**不要提交这个文件**）：

```yaml
competition:
  market: ctp

market_data:
  ctp:
    md_front: "tcp://<前置IP>:<端口>"
    broker_id: "8888"
    user_id: "你的投资者编码"
    password_env: CTP_PASSWORD      # 只写环境变量名
    instruments: {}                 # 留空 = 按持仓量自动选主力
    auto_months: 12
    bar_seconds: 60                 # 必须能整除 300 秒（快照每次都先要 5m）且不短于 10 秒
    dominant_stale_sec: 300         # 合约安静这么久（按观察到的交易时长算）就退出主力候选
    max_bars: 3600                  # 每个品种保留多少根基础 bar，下限随 bar_seconds 反比缩放
    persist_bars: true
```

密码放环境变量，不要写进文件（`password` 字段只是本地应急用；无论走哪个字段，
CTP 的密码与投资者编码都**不会**进入竞赛存档 `competitions.config_json`）：

```powershell
setx CTP_PASSWORD "你的密码"
```

## 四、两个必须知道的设计取舍

### 1. K 线是本地从 tick 聚合出来的

CTP **只推 tick**（最新价、买卖一档、当日累计成交量、持仓量），**不提供历史 K 线**。
所以 1 分钟 bar 由引擎自己累，5m/15m/1h 再由 1m 重采样。

后果是**冷启动的指标要攒很久才齐**，而且比直觉久得多。`summarize()` 对**每个周期各自**都要
60 根才给得出 `ema60`（`macd` 要 35 根），所以要按"每个周期各凑 60 根"算。

数的是**对齐的桶**，不是交易小时数：`resample()` 按 `ts - ts % 周期` 分桶，横跨开收盘的那个桶
只要有成交就算一根。比如 IF 的 09:30–11:30 与 13:00–15:00 产出 09、10、11、13、14 五个 1h 桶，
而不是 4 个（它每天只有 4 个交易小时）。按本仓库的 `config/contracts_cn.json` 逐品种数下来：

| 周期 | 每交易日的桶数 | 凑齐 60 根要几个交易日 |
|---|---|---|
| 5m | 45～111 | 0.5～1.3 日 |
| 15m | 15～37 | 1.6～4 日 |
| 1h | 5～11 | **5.5～12 日** |

1h 那一列的两端：黄金/白银/原油每天 11 个桶（5.5 日）→ 有色 9 个（6.7 日）→ 螺纹等 43 个品种
7 个（8.6 日）→ 国债 6 个（10 日）→ 股指与无夜盘品种（鸡蛋、生猪等）5 个（**12 日**）。

也就是说：跑满一小时只出**第一根** 1h bar；要让 1h 的慢指标真正齐，最快的品种也要一周多，
慢的要两周半。这期间模型拿到的 1h 指标是缺的，而且不会报错——**开真钱实验之前要把这段算进去**。

引擎会把 bar 落进 SQLite 的 `md_bars` 表（`persist_bars: true`），下次启动自动预热，
所以这个代价只在**第一次**启动时付一次，之后重开软件都是接着跑。

> 先用 `market: cn_futures` 跑一段**不能**给 CTP 攒历史：落库只对 CTP 源生效，新浪跑多久
> `md_bars` 都是空的。两边的 bar 来源与口径也不同，混在一起用不安全。目前没有从新浪导入
> 历史的通道，第一次接上 CTP 就是要从零开始积累。
>
> 另外，`bar_seconds` 改了之后旧的历史不会被读回来（库里按基础周期分开存，`md_bars` 的主键
> 含 `bar_seconds`）——这是有意的：把一分钟的 bar 当成五分钟用，指标会错而且不报错。
> 两个周期各存一份、互不覆盖，所以再换回去时那一份历史仍然完整；代价是停用的周期会留着
> 最多 `max_bars` 根，只在重新写入该周期时才裁剪。
>
> **换行情前置或改钉死的合约同理**：`md_bars` 的主键还含一个 `feed` 指纹——**按品种**算的
> （前置地址、broker、**该品种**钉死的合约、`auto_months`、主力选取参数与 `bar_seconds` 的摘要）。
> 这些一变就是另一条价格序列，旧的那一份不会拿来预热新的，新写入的也不会续在旧的后面——否则
> 排行榜虽然重开了，指标与历史仍然是两场实验缝成的一条。同样是换回去就还能找回那一份历史。
> 指纹按品种而不是按整份配置算：否则把一个本来就钉好、只是还没参赛的品种放进 `symbols`，
> 会把所有品种攒下的历史一次性弃掉，而且不报错。
>
> **升级到这一版时，CTP 的历史要重新积累一次。** 升级前那批 bar 没有来源标记，据配置反推
> "它们是哪套接入累出来的"三种依据全被证伪过：升级与换前置可能在同一次重启里发生；上一场
> 竞赛可能根本没跑过这个品种；`persist_bars` 关着时判定会被推迟到另一套接入之后才做。反推
> 错了不报错，只会把另一条价格序列喂进指标，所以干脆不反推——那批行留在空命名空间里，不删
> （删的是使用者的数据），也永远不会被读回。代价是一次性的：1h 的慢指标要重新攒 5.5～12 个
> 交易日，日志里看得见（预热 0 个品种）。

`max_bars` 是**每个品种**在内存里保留的基础 bar 根数，它的下限随 `bar_seconds` 反比缩放：
1h 的 `ema60` 要 60 根 1h，也就是 `60 × 3600 ÷ bar_seconds` 根基础 bar（`bar_seconds: 60`
→ 3600 根，`30` → 7200 根）。配小了不会报错，只是 `klines("1h")` 永远凑不满 60 根，
ema60/MACD/布林这些 1h 慢指标对模型**永久缺失**，看上去和「冷启动还没跑满」一模一样。
因此行情源在启动时会把配小的值抬到这个下限并记一条 warning——代价是内存：
把 `bar_seconds` 降到 30 秒，保留根数会翻倍，80 个品种大约多占一百多兆。
反过来，这也是 `bar_seconds` 有 10 秒下限的原因：1 秒的 bar 每个品种要留 216000 根才凑得出
1h 的 ema60，而 CTP 的行情本身是 500ms 一档的快照，再细也没有新信息。

> `competition.timezone` 只管看板怎么显示。CTP 推的 `ActionDay`/`UpdateTime` 和合约表里的
> 交易时段都是**交易所本地时间**，行情源固定按 `Asia/Shanghai` 解释，不跟随显示时区——
> 跟随的话，`timezone: UTC` 下每一条 tick 都会被当成八小时后的未来行情整批丢掉。

### 2. 主力合约是按持仓量自动选的

CTP 订阅的是**具体合约**（`rb2601`），没有「主力连续」这种东西——新浪的 `RB0` 是它自己合成的。
本项目的做法：按品种枚举未来 `auto_months` 个月的候选合约（按各交易所的命名规则，
郑商所一位年份 `SR601`，其余两位 `rb2601`），全部订阅，再**按持仓量最大**选出主力。
这是行业通行口径，换月也会自动跟随。

`auto_months` 是**下限**：窗口至少延到当月之后下一个挂牌的交割月。当月合约在当月中途就到期
（股指第三个周五、国债第二个周五、商品多在中旬），之后到月底它一笔 tick 都不再有；只订当月的话，
那个品种要等日历翻月才重新有行情。交割月稀疏的品种（国债只有季月，苹果没有 6～9 月）用 2、3 个月
的预算也会撞上同样的空档，所以按品种的挂牌规则往后延（`arena/market/ctp.py` 的
`LISTED_DELIVERY_MONTHS`，只用来延长、绝不用来收窄——写错的代价只是多订几个不存在的合约）。
窗口还会跟着交易所日历往前推：进程跨月时按当天重新枚举，新进入窗口的合约自动补订，不必重启；
已订的不退订（到期合约不再报价，选主力时按活跃度自然退出）。

想钉死某个合约就写进 `instruments`：

```yaml
    instruments: { RB0: rb2601, AU0: au2512 }
```

钉死的品种不参与自动换月。

## 五、验证

```bash
python run.py --headless --config config/config.yaml
```

看板的「行情源」应当显示 `ctp`、`ok`，detail 里是 `已登录，N/M 个合约有行情`。
N 通常小于 M——没挂牌或没人交易的候选合约不会有 tick，这是正常的。

常见问题：

| 现象 | 原因 |
|---|---|
| `连接 CTP 行情前置超时` | 前置地址或网络不通；确认是**行情**前置不是交易前置，确认在交易时段 |
| `CTP 行情登录失败：[3] CTP:用户口令校验失败` | BrokerID / InvestorID / 密码有一项不对；程序化密码可能与终端密码不同 |
| 登录成功但一直没有行情 | 多半在休市时段；也可能是合约代码规则不对（尤其郑商所的一位年份） |
| `未安装 CTP 行情 SDK` | `pip install openctp-ctp` |

## 六、本项目**不做**实盘交易

接的只有行情。撮合、持仓、盈亏全部在本地模拟盘里完成，**不会向交易前置发送任何委托**，
代码里也没有引入交易 API。真要接实盘是另一件事，风险与合规要求完全不同。
