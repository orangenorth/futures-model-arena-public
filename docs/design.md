# 架构与数据模型

## 进程结构

```
run.py (主线程)
 ├── uvicorn 线程 ──► FastAPI (arena/server/api.py)：只读查询 + 控制接口 + 静态看板 web/
 ├── 引擎线程 ──► Engine._run()（arena/engine/loop.py）
 │     ├── 每 tick_interval_sec：MarketSource.latest()（各品种并发，整体耗时以 timeout 为上限）→ 盯市 → 止损/止盈/强平 → 成交落库
 │     ├── 每 snapshot_interval_sec：权益快照、日汇总、指标重算
 │     ├── 每 decision_interval_sec（开市时）：构建共享 MarketSnapshot → ThreadPool 并行 4 个 Trader.decide()
 │            → RiskManager.check() → SimExchange.open/close/adjust → decisions/trades/accounts 落库
 │     └── 盘前研究线程（可选，国内真实市场）：冻结一份无账户的 MarketSnapshot → 4 份独立陈述 → 4 份互相反证
 │            → debate_sessions/debate_turns 落库 → 人工 Codex 仲裁包；绝不进入 RiskManager 或 SimExchange
 ├── 看门狗线程：引擎线程死亡即重启
 └── pywebview 窗口（或系统浏览器 / headless）
```

## 模块

| 模块 | 职责 |
|---|---|
| `arena/config.py` | pydantic 配置模型；`load_config()` |
| `arena/models.py` | Bar / Quote / ContractSpec / Position / Account / Trade / ActionRequest / Decision |
| `arena/db.py` | SQLite WAL；表：competitions, traders, accounts, positions, trades, decisions, equity_snapshots, daily_summaries, events, `debate_sessions`, `debate_turns`, kv |
| `arena/debate.py` | 只含无账户的市场事实清单、严格观点/反证解析与人工 Codex 仲裁包；不依赖交易执行对象 |
| `arena/market/*` | `MarketSource` 接口；`sina_cn`（新浪轻量当前报价 + 分钟线）、`crypto`（OKX/Binance 公共接口）、`replay`（合成/CSV 回放）、`indicators` |
| `arena/exchange/contracts.py` | 合约规格、交易时段判断（含夜盘跨日、节假日） |
| `arena/exchange/sim.py` | 模拟撮合：滑点、手续费、保证金、止损止盈、强平 |
| `arena/engine/risk.py` | 硬风控与动作修正 |
| `arena/engine/metrics.py` | 收益率、最大回撤、Sharpe、胜率、盈亏比 |
| `arena/engine/loop.py` | 主循环、恢复、熔断、状态输出 |
| `arena/traders/*` | `prompt.py`（统一模板 + 解析）、`llm.py`（OpenAI 兼容）、`rule.py`（演示策略）、`MockTrader`（测试） |
| `arena/server/api.py` | REST 接口 |
| `arena/desktop.py` | 桌面壳 |

## 决策输出 schema

```json
{"analysis": "…", "actions": [
  {"symbol": "RB0", "action": "open_long|open_short|close|adjust_sl_tp|hold",
   "size_pct": 0.15, "leverage": 1, "stop_loss": 3350, "take_profit": 3520, "confidence": 0.65, "reason": "…"}
]}
```

解析容错：去掉 ``` 包裹、截取首个 `{…}`、去尾逗号、动作别名（buy/sell/long/short/exit）、品种别名（rb2510 → RB0）、百分数 size。

## 模拟交易所规则

- 国内期货：数量为手；名义 = 价 × 乘数 × 手；保证金 = 名义 × 保证金比例；手续费按手或按名义比例（`config/contracts_cn.json`）。
- 加密永续：数量为币；保证金 = 名义 / 杠杆；逐仓强平：亏损 ≥ 保证金 × (1 − 维持率)。
- 通用：市价按最新价 ± 滑点成交；同一品种不能同时多空；风险度 = 占用保证金 / 当前权益。公开模板把
  `target_margin_risk_min_ratio` 设为 0.80、`target_margin_risk_max_ratio` 设为 0.90：这只是有充分信号、报价新鲜且止损可定义时的
  条件性目标带，不会为了凑仓位自动开仓；达到 90% 后正常开/加仓不再增加风险。`max_margin_risk_ratio` 保持 0.95：新开/加仓先按
  全账户合计风险度做准入，实际成交价、滑点与手续费确定后再由撮合器复核；目标带启用时，实际成交后超过 90% 原子拒绝，目标带关闭时
  等于 0.95 可接受、超过 0.95 原子拒绝，不改变账户。目标带与硬上限均可配置；配置模型保留 `None` 默认值以兼容旧配置，
  而公开产品模板显式启用 80%–90% / 95% 规则。
  `liquidation_risk_ratio` 保持 1.0，价格波动后风险度达到该最终阈值、或权益 ≤ 0 时才全部强平。
  全账户强平一次平掉全部持仓：本 tick 没有报价的品种按候选账户的最新价平仓（通常是持久化值；若有未落库的盯市日志，先用其记录的值），
  不会留着敞口却已计一次强平。
- 止损止盈每 tick 检查；`min_hold_sec` 内模型不能主动平仓（止损止盈不受限）。

## 持久化与恢复

- 状态以数据库为准：账户、持仓每次变动后立即写库；启动时读取 `status='running'` 的竞赛与账户继续。
- 重置 = 旧竞赛标记 `ended`，新建竞赛；历史数据保留，可用 `scripts/export_results.py --db [--competition ID]` 导出。
  重置前先按记录的原价补做旧竞赛尚未落库的触发成交（止损/止盈/强平），补不了则拒绝重置（`/api/control` 返回 409，看板提示稍后再试）：
  归档后启动只恢复进行中竞赛的预写日志，直接丢弃会让这笔成交从旧竞赛的结果里永久消失。
  新竞赛的创建与它沿用的回放位置、暂停标志在同一事务写入：写不进去就整体回滚、拒绝重置，旧竞赛保持进行中，
  不会出现"新竞赛已建立却没有回放位置、重启后从最初历史重放"的状态。
  启动时因配置变化（市场/起始资金/时区/总保证金开仓准入上限）自动切换竞赛也一样：先按旧竞赛创建时持久化的配置（市场、合约表、风控参数）补做，
  补不了则拒绝启动（`RolloverBlocked`，退出码 3），旧竞赛保持进行中。
- 启动恢复同一竞赛时，先按原触发价补做预写日志里的触发成交，再做配置对齐（移除的交易员不再参赛、移除品种的持仓按最后价平掉）；
  补不了的账户推迟对齐，等 tick 重试成功后再对齐——否则对齐会先删掉账户/平掉持仓，原触发价的成交被替换或丢弃。
  关闭前未写入的盯市更新还写不进去的账户同样推迟：否则会按陈旧的库内最后价平掉已移除品种、或删掉账户，随后重试找不到
  持仓/账户而清掉日志，记录的价永久丢失。
  推迟期间，已移除品种的持仓按合约表全集/默认规格估值（`engine.specs` 对配置外品种回退到 `_spec_for`），
  已移除交易员的暂留账户不进排行榜；看板与账户视图照常工作。
- 无成交的盯市也会改持久化字段（持仓最新价、权益峰值）：同样先落库再发布；落库失败时内存保持旧值（估值用的是最新行情，
  不受影响）、下个 tick 再试，不算待重试触发；回放源同样保留这根 bar 重放、位置不前进，直到写入成功——否则重启后位置在这根 bar
  之后而数据库里的最新价还是更早的。这样崩溃重启后对齐平仓用的最新价是崩溃前最后一根已落库 bar 的值。
  重放时若已无差异可写（例如在飞的决策随后平掉了持仓并落库），解除保留；重置前也先补写这些更新，写不进去则拒绝重置。
  失败那次算出的权益峰值被记住，之后任何一次成功的账户写入（重试盯市、决策落库、关闭时的最终持久化）都把它并入；
  实时源没有新报价（收盘、行情源故障）或只来了部分品种的报价时，都按完整的缓存价补写，不等下一个可用报价。
  关闭前仍写不进去的盯市更新以独立类型（`kind: mark`：各持仓最新价 + 记住的权益峰值）记入预写日志，重启后与每个 tick 开头、
  重置前、归档结算时直接写入——不经过撮合器：它只是当时已算过且无成交的结果，按现在的风控参数或合约表重新盯市可能凭空产生
  当时并不存在的强平；写入提交前条目与日志都保留，重启时数据库仍不可写也不丢。写入前该账户只按新收到的报价做逐品种触发评估；
  本 tick 没有报价的品种先把日志记录的价置入候选账户，但不重做其止损/止盈/逐仓强平。这样当前 tick 若因其他新报价触发账户级强平，
  权益计算和该缺席品种的成交都用同一日志价；未触发时该值只随成功写入持久化。按缓存价的补写（收盘无报价、关闭、重置）都跳过它，
  只直接写入；
  直接写入时并入重启后已收到的报价（各自 tick 已评估过、无成交）与记住的高水位——并入的值先进日志、再进数据库（日志写不进去则
  本次不写数据库），否则数据库提交后、日志清理前退出，重启会把日志里的旧价盖回新状态；更新还没写进去期间按新报价的无成交盯市
  写入同样先把并入后的值写进日志。写入前该账户的决策动作与触发待落库时一样只记
  零成交的拒绝审计——实时源没有回放那样的整体停住，数据库恰在决策落库时恢复、决策改了持仓之后，写入的日志价会盖掉更新后的状态。
  回放源：日志同时记下关闭时保留的那根 bar 之后的回放位置，重启按它恢复，日志全部写入后才把位置写入 `kv`，期间不取新 bar、
  不开新一轮——不重放那根已在所有账户上评估过的 bar（重放会按现在的条款重新评估它）。触发待重试的账户不用缓存价再盯市
  （那会用此刻的价格覆盖记录的原触发价），记住的高水位随触发条目进日志、重试落库时带上；同一账户既有触发又有未写入的更新时
  两者都记在日志里；触发重试无成交时也先写入再清条目。关闭时的兜底保存跳过这些账户，不写"旧最新价 + 新峰值"的半截状态。
  关闭时预写日志主/备用位置也都写不进去：不报"已记入"，ERROR 日志记下数值、事件与 `Engine.shutdown_errors` 标明未持久化。
  这类更新写入数据库后，旧日志副本删不掉且墓碑也写不进去时，该账户与触发的情形一样封锁（`_journal_stale`）、每个 tick 重试
  清理，成功前不执行其决策——否则崩溃重启会把日志里的历史价套到之后新开的持仓上。日志最后一条写入后先把回放位置写进 `kv`、
  再清日志；位置写不进去时只剩位置的空日志/墓碑保留（不删），重启从它恢复位置；日志里的位置只有比 `kv` 里的新才采用，
  残留旧副本里的位置作废，不会让回放倒退或停住。
- 回放 bar 被保留（任一账户的结算或盯市更新未落库）或回放位置待写入期间，所有账户迟到的决策动作一律只记零成交的拒绝审计，
  `_round` 在发起模型调用前也复查这两个状态并整轮放弃——否则成交会记在持久化位置之后的 bar 上，崩溃重启重放该 bar 时又对
  已改变的账户再决策一次。
- 合成行情按跳价取整后每个 OHLC 字段至少一个跳价（起始价低于一个跳价的配置直接拒绝），不会产生 0 价进入指标计算。
- 市场、起始资金或时区与进行中的竞赛不同（对比竞赛创建时持久化的 `config_json`）→ 结束旧竞赛并新建，不混入同一排名。
- 暂停状态、日初权益（含上一次快照的权益/成交数/手续费，作为跨日基线）存在 `kv` 表，重启后保持。
- 止损/止盈/强平触发：先把原触发价与时钟写入与 SQLite 无关的预写日志文件（`data/pending_marks_<竞赛id>.json`，原子替换；
  数据目录写满/只读时退到系统临时目录 `futures-arena/<数据库路径哈希>/` 下的备用位置；每份带版本号，重启时读两处并以最新为准；
  结算后旧副本删不掉时写版本更新的空墓碑，避免旧触发价被套到之后的新持仓上；墓碑也写不进去时该账户保持封锁、
  每个 tick 重试清理，成功后才恢复决策；日志同时记录触发时生效的条款——撮合参数（滑点、强平阈值）与所涉品种的合约规格快照，
  重试按这些条款重建撮合器补做，不受重启后风控参数变化或合约表事后编辑的影响），再落库；落库失败则下个 tick（不依赖新行情，收盘后/行情源故障时数据库恢复了也立刻结算）或重启后先按原触发价重试，
  期间该账户的模型动作一律不执行——实时行情的下一根未必再穿越触发价，不能靠"下次再看"。成功后清除日志。
- 回放源在每个 tick 所有账户处理完这根 bar 后（某账户的触发成交落库失败则下个 tick 重放同一根 bar，不前进，主循环也不开始新一轮），把回放位置（advance 步数、合成起点、各品种时刻/价格）写入 `kv`
  （`replay_pos:<竞赛id>`；重置时也为新竞赛写一份）。重启后按 seed 确定性快进同样的步数，随机序列、滚动 bar、趋势/波动状态
  与 CSV 游标都与上次一致；CSV 或配置已变时退化为按上次时刻/价格近似衔接。不会把同一段行情再放一遍。
  回放位置写入失败时不取下一根 bar（不前进）、不开始新一轮决策，写入失败前已发起、此时才返回的模型决策也只记零成交的拒绝审计
  （否则决策会记在持久化位置之后的 bar 上，重启重放时对已改变的账户再决策一次），每个 tick 与关闭时重试写入，成功后才继续：
  持久化的位置最多落后一根已全部结算的 bar，重启重放它对已成交的止损/止盈是幂等的，不会重复成交，也不会让之后的成交跑到行情前面。

## 赛前多空决策室（研究性、不可执行）

### 调度与输入边界

- 自动调度只在 `market=cn_futures` 且不是加速回放时启用；根据交易日历的下一次开盘，仅支持 09:00、13:30、21:00 三个盘前阶段。
  `lead_window_sec`（模板 1,800 秒）内同一交易时段最多预占一场。手动发起也复用同一研究链路，但从不等价于“立即决策”或“立即下单”。
- 自动与手动会话都先单独拉取行情，建立一份不含账户、持仓、订单、交易员历史或凭据的 `MarketSnapshot`。正常快照将报价和 5m/15m/1h
  指标转换为带事实 ID 的清单，并以规范化内容生成 `analysis_id` 与 `snapshot_hash`；四个参与者看到的是同一份冻结输入。
- 在 `market=cn_futures` 时，同一会话还会用独立的只读扫描器取得全量候选目录的 5m 技术结果。每个候选都以 `scanned`、
  `catalogue_excluded` 或 `runtime_excluded` 状态冻结在会话快照中；只有目录通过候选全部完成扫描时，才允许四个模型继续。模型输入
  只包含确定性全量宽度、交易所汇总和固定数量的代表性事实，完整逐合约行不会进入 prompt，也不会扩展 `symbols`、风控、撮合或订单路径。
- 自动会话始终要求完整的 5m/15m/1h 执行池快照。只有用户显式点击手动研究、每个执行池品种即时报价均新鲜、但分钟线端点临时不可用时，才允许构建
  `history_quality=quote_only` 的降级快照：指标字段为空、置信度固定为低，并写入“不能据此推断趋势延续”的失效条件。该降级仍须通过全量目录通过候选的
  5m 覆盖闸门；覆盖不完整时会话记录为 `unavailable`，不调用模型。该降级从不用于自动调度、正常决策或交易执行。
- 手动研究即使竞赛已暂停也可发起：它捕获当前 `decision_epoch` 并保持暂停，不会开启执行窗口；若用户随后恢复、重置或停止竞赛，epoch /
  generation 校验会使该研究会话中止，避免在不同的竞赛状态上继续写入。
- 模板要求行情源健康、全品种覆盖，且最近一次成功刷新不超过 `max_quote_age_sec`（模板 900 秒）。盘前允许使用上一交易时段的
  最后报价；“允许上一根报价”不等于“允许一个长期失联的行情源”。源级 `last_ok` 不足以代表全集：CTP 是订阅推送，它只是
  **任意**一个已订阅合约最后一条 tick 的到达时刻，集合竞价里一个品种报价就能刷新它，而其余品种缓存的已发布报价可以任意陈旧。
  因此还要逐品种校验——**自动**研究的范围是这次开盘时刻真正开市的那些品种（`is_open(开盘后一分钟, symbol)`），不是全部配置品种：
  夜盘只有一部分品种上市，拿全集去要求新鲜报价会让股指等只有日盘的品种把夜盘研究永久挡死。**手动**研究没有"这次要开的盘"可以据以
  缩小范围，快照覆盖的也是全部配置品种，因此要求每个配置品种都新鲜——按"此刻开市"缩小的话，休市时那是空集，等于这道闸门不存在。
  预约闸门与调模型前的闸门判同一件事，否则预约照样会被白白烧掉。无法建立统一快照时只记录研究启动失败事件且不调用模型；
  快照已冻结但健康/覆盖条件不满足时，预占会话记录为 `unavailable`，同样不调用模型。
- 只有恰好四个配置交易员且四者都是可用的 `LlmTrader` 才会继续。演示策略、熔断替身或缺少 Key 不会生成虚构观点；会话记录为
  `unavailable`，不会产生任何付费研究调用。

### 两阶段辩论与仲裁

1. **开场**：四个模型并发、独立地给出 `bullish` / `bearish` / `neutral` 立场、置信度、论点、最强反方、失效条件与不确定性；
   每项论据必须引用冻结清单里的有效事实 ID。
2. **反证**：仅在四份有效开场都落库后，四个模型针对其他参与者的一份开场观点反证并修订自身判断。第一轮文本被当作不可信数据，
   不能改变系统规则或调用外部操作；第二轮仍只能引用同一事实清单。
3. **仲裁**：两轮各四份都完整时，系统输出结构化的初步分歧摘要和可复制的 Codex 仲裁包。仲裁包由人手交给 Codex 审阅，
   不会自动使用 ChatGPT/Codex OAuth 额度，也不会把任何裁决反馈给订单执行器。

每轮有独立的短截止时间、无重试；取消状态检查与一批模型请求提交串行化，暂停、重置或停止不会插入检查与付费提交之间；一轮超时、解析失败、暂停、重置或重启都会持久化为 `incomplete` / `aborted` 等终态，
不补造缺失观点、不跳过第一轮直接反证。完整会话最多 8 次模型调用。研究线程与正常决策线程分离：它不创建 `Decision`、`Trade`、
账户或持仓变更，也不读写 `RiskManager`、`SimExchange` 的执行路径。

### 可回放性、隔离与 API

- `debate_sessions` 在调用模型前以 `(competition_id, session_key)` 唯一预占，且只在竞赛仍为 `running` 时插入，防止主循环的重复 tick 对同一盘前时段重复付费。全量扫描在锁外，预占前要在引擎锁与提交门闩下复查生命周期；
  `debate_turns` 以阶段和参与者唯一，按配置顺序保存结构化结果。重启会把遗留的运行中会话标为中止，新的竞赛不会接续旧竞赛的会话。
- 会话归属当前竞赛，详情读取也必须带当前 `competition_id`；猜测历史会话 ID 不能跨竞赛读取。`GET /api/debates` 返回紧凑历史，
  `GET /api/debates/{id}` 返回冻结事实、结构化观点与仲裁包，但不会返回原始模型 prompt/response 或错误原文。失败回合仅可投影
  固定的脱敏 `failure_category`（如超时、连接、认证、限流、额度、上游 4xx/5xx、结构校验或阶段截止）；未知或历史错误不伪造精确原因。
  仲裁包同样只能引用固定失败说明，不能嵌入 SDK body、URL、请求头或供应商错误文本。`POST /api/debates/run`
  默认只允许本机控制路径显式启动研究（远程控制须显式配置），不触发交易。
- 赛前自动研究不在 `replay` / `--accelerate` 中运行，避免把墙钟盘前调度混入回放时间轴。竞赛本身仍按创建时保存的
  市场、时区、本金、总保证金开仓准入规则和参赛阵容保持公平；`initial_cash`、市场、时区、目标风险带、`max_margin_risk_ratio` 或真实模型阵容变化会另开竞赛，
  不与旧排行榜混合。预警、强平及其他既有执行调参（例如滑点）不作为竞赛身份键，未落库触发仍按预写日志中保存的历史条款补做。
- 决定**价格序列长什么样**的行情接入与聚合设置同样是竞赛身份键（`MARKET_FEED_FIELDS`）：CTP 的
  `md_front`、`broker_id`、`instruments`、`auto_months`、`bar_seconds`、`max_bars`、`discovery_grace_sec`、
  `dominant_stale_sec`、`persist_bars`，以及 crypto 的 `provider`。把 RB0 换钉到另一个合约或改 `bar_seconds`，
  K 线、指标与模型看到的证据全都不同（落库的 `md_bars` 还会拿旧设置的 bar 给新设置预热），继续沿用同一张排行榜
  等于把两场性质不同的实验混在一起。只影响"连不连得上"的设置（`connect_timeout_sec`、`flow_dir`、各源的超时）不在其中。
  `max_bars` 按源实际生效的值（不足保留下限时会被抬上去）比较，按品种索引的映射只取当前参赛的那些键。
  `replay` 有意不在此列：合成/CSV 回放换了数据时，引擎已有"近似衔接"通道继续同一场竞赛。凭证字段从不参与比较。

## 稳定性

- 行情/LLM 请求：超时 + 指数退避重试；行情失败只记日志，下一 tick 重试。盯市用的 `latest()` 每品种只请求一次且并发进行，
  超过预算未返回的品种本次跳过、后台继续（完成后的结果在下个 tick 先交付，再发起新请求），止损/止盈/强平检查不会被慢行情源拖住。
- 看板轮询 `/api/state` 的 `data_version`（决策结算、成交、事件写入后递增）决定何时刷新决策日志与事件表。
- 行情解析（新浪、OKX/Binance、CSV 回放）拒绝 NaN/Infinity 与非正价格的行；CSV 导出时间按竞赛时区（离线导出取竞赛创建时持久化的时区）。
- 回放源有自己的时间轴：成交（含各品种各自时刻的止损/止盈/强平）、持仓时长、权益快照与日汇总都按回放行情时间戳记账；
  看板的权益时间范围（1天/1周/1月）相对最新快照计算，而不是浏览器时间。实时源全部用墙钟。
- 单模型：超时或非法 JSON 记为错误 HOLD；连续 `breaker_failures` 次触发熔断跳过 `breaker_skip_rounds` 轮。
- 写接口只接受同源请求，且在**中间件里按请求方法统一拦截**（`POST`/`PUT`/`PATCH`/`DELETE`），不是每个路由各自调用检查：
  单个路由里的一次调用只保护它自己，以后新增的写接口会默认失去保护，而这类接口往往正是花钱或改竞赛状态的那种。
  判定按 `Sec-Fetch-Site`（其次 `Origin` 与 `Host` 比对），`Origin: null`（sandbox iframe、file://）同样拒绝；没有这两个头的
  客户端（桌面壳、curl、脚本）不是浏览器发起的跨站请求，照常放行。只判断"对端是回环地址"不够——本机浏览器打开的任意网页，
  其请求的对端同样是回环地址，否则恶意页面猜到端口就能重置竞赛。中间件在路由之外运行、异常处理器不接管，所以它直接构造
  与 `HTTPException` 相同 `{"detail": …}` 形状的 403。读接口不受影响（跨站读取的响应本来就被浏览器同源策略挡住）。
- 同一中间件还校验 `Host`：只有回环名字（`127.0.0.1` / `localhost` / `::1`）与配置里绑定或列出的主机名能发写请求。
  只看来源头挡不住 **DNS 重绑定**——攻击者把自己域名解析到 `127.0.0.1`，受害者访问 `http://evil.example:<端口>/` 时
  请求就落到本机看板上，而 `Origin`、`Host` 与 `Sec-Fetch-Site: same-origin` 此时全部合法。绑定 `0.0.0.0` 供局域网访问时，
  合法主机名无法从配置推出，需要用 `server.allowed_hosts` 显式列出。没有 `Host` 头的客户端放行：浏览器必发 `Host`。
  桌面壳给出的看板地址由 `desktop.client_host()` 决定，通配绑定时一律用回环（`http://0.0.0.0:<端口>/` 既连不上，
  也不是合法的看板 Host，控制请求会被上面这条拒掉）。
- 盘前研究：四模型并发但每阶段使用独立截止时间；研究请求没有常规决策的重试/熔断副作用，不能因研究失败改变参赛模型的正常 JSON 能力。
- 主循环 catch-all；看门狗 30s 巡检；日志 RotatingFileHandler（5MB × 5）；SQLite WAL + 周期 checkpoint。
- 国内市场休市时只盯市不决策；看板显示下次开盘时间。
